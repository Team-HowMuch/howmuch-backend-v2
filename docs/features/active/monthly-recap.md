# Feature Plan: 월 리캡 기본 집계·저장·조회

- 상태: 후속 구현 진행
- 작성일: 2026-10-13
- 관련 이슈: [#478](https://github.com/Team-HowMuch/howmuch-backend-v2/issues/478), #482~#488
- 관련 ADR: [Capability-oriented Output Ports](../../adr/0003-capability-oriented-output-ports.md)

## 1. 목적

완료 정산을 바탕으로 회원의 월별 정산 건수·본인 부담액·전월 비교·가장 많이 함께한 사람을 생성 시점에 고정 저장한다. 현재는 리캡 알림 수신 경계만 있고 집계·저장·조회 기능이 없다.

### 완료 기준

- [ ] KST 완료 월과 본인 부담액으로 요약한다.
- [ ] 생성 이후 원본 변경·삭제와 재실행으로 결과가 바뀌지 않는다.
- [ ] 본인 권한으로 월 목록·개인 상세·공유 데이터·고정 사진을 조회한다.
- [ ] 누락·실패·동시 실행을 복구하고 다른 회원의 처리를 계속한다.
- [ ] 탈퇴 시 본인 리캡만 삭제하며 다른 회원의 고정 표시 정보는 보존한다.

카테고리·기록·인사이트·혜택·알림 발송·공유 이미지 생성은 제외한다. 알림 연동 #474는 종료하지 않는다.

## 2. 도메인과 확정 규칙

`recap`은 여러 정산과 회원 표시 정보를 조합한 고정 보고서다. 원본 정산과 독립적인 저장 수명과 월 생성 작업이 필요하므로 별도 영역으로 둔다.

### 월 요약

- KST 월 시작 이상, 다음 달 시작 미만에 완료된 `COMPLETED` 정산을 집계한다. 기존 계약대로 `updated_at`을 완료 시각으로 해석하고 UTC 조회 경계를 적용한다.
- 생성자 또는 저장된 `linkedUserId`로 참여한 정산을 중복 없이 센다.
- 생성자 몫을 포함한 본인 Share 부담액을 합산한다. 입금액·정산 전체 금액·전화번호 추론·이후 회원가입 연결은 사용하지 않는다.
- 정상적인 품목 0원 제출은 포함하고, 불완전한 Share 누락은 회원별 생성 실패로 처리한다.
- 완료 정산이 1건 이상이면 부담액 0원이어도 생성한다. 생성 전에 삭제된 정산은 제외한다.

### 전월 비교

직전 달의 저장된 리캡과 비교한다. 다른 달이나 원본 정산으로 대체하지 않는다.

| 조건 | 상태 | 차액 | 변화율 |
|---|---|---|---|
| 직전 달 리캡 없음 | `NO_PREVIOUS` | `null` | `null` |
| 전월 0원, 이번 달 양수 | `PREVIOUS_ZERO` | 이번 달 금액 | `null` |
| 양쪽 모두 0원 또는 같은 양수 | `UNCHANGED` | 0 | 0.0 |
| 증가·감소 | `INCREASED`·`DECREASED` | 이번 달 − 전월 | 부호 있는 백분율 |

`BigDecimal`과 `HALF_UP`으로 소수점 한 자리까지 계산한다. 상태는 반올림 전 실제 차액으로 판단한다. 합계는 `long` 범위를 넘으면 실패하며 잘못된 금액으로 저장하지 않는다.

### 함께한 사람과 개인정보

- 본인을 제외한 참여자를 대상으로 회원은 계정 ID, 비회원은 공백 제거·영문 대소문자 통합 이름으로 묶는다. 회원·비회원 식별 공간은 분리한다.
- 정산별 같은 동행자는 한 번만 세고, 함께한 금액은 해당 정산들의 본인 부담액 합계다. 상대가 0원 제출이어도 포함한다.
- 횟수 내림차순 → 본인 부담액 합계 내림차순 → 표시 이름 가나다순 → 고정 식별자순으로 한 명을 선정한다.
- 회원은 생성 시점 계정 이름을 개인 조회에, `publicId`를 공유에 사용한다.
- 비회원은 가장 최근 완료 정산의 원래 이름을 사용한다. 완료 시각까지 같으면 정산·참여자 ID로 순서를 고정한다.
- 비회원 공유 이름은 첫·끝 글자만 남긴다. 두 글자는 `김*`, 한 글자는 `*`이며 Unicode 코드 포인트 단위로 처리한다.
- 생성 전에 탈퇴한 회원은 `탈퇴한 회원`과 기본 이미지로 표시한다. 탈퇴용 공개 아이디는 노출하지 않는다.
- 동행자가 없으면 `companion: null`이다.
- 본인 이름과 선정된 동행자의 개인·공유 표시 이름 및 사진을 고정 저장한다.
- 본인 탈퇴 시 본인 리캡·작업·사진을 정리한다. 다른 소유자의 기존 복사본과 표시 정보는 유지한다.

## 3. 흐름과 실패 처리

최초 활성화 시 직전 달을 최초 대상 월로 한 번 저장한다. 더 오래된 기록은 생성하지 않는다. 매월 1일 KST 00:10 및 매시 10분에 최초 대상 월부터 직전 달까지 누락·실패를 확인한다. 시작 시에도 복구한다.

월을 오래된 순서로 등록한 뒤 회원별 이전 미완료 작업을 먼저 처리한다. 이전 월 생성 실패는 해당 회원의 다음 월만 보류한다. 완료 정산 0건 또는 비활성 소유자는 `SKIPPED`로 종료한다.

생성 작업은 `PENDING → PROCESSING → COMPLETED/SKIPPED` 또는 `PROCESSING → RETRY → PROCESSING`으로 진행한다. 10분 점유 만료·토큰 검증·점유 갱신으로 오래된 작업의 저장을 차단한다. 스냅샷 삽입과 작업 완료는 같은 트랜잭션이다.

사진이 원래 없으면 `avatarUrl: null`이다. 사진이 있는데 복사에 실패하면 회원 작업을 재시도한다. 예약 파일명과 정리 작업을 영속 저장해 실패·점유 만료·탈퇴·비정상 종료 잔여 파일을 정리한다. 활성 예약이나 저장된 스냅샷에서 참조 중인 파일은 삭제하지 않는다.

## 4. 계약

### API

모든 API는 `CurrentActorPort`로 본인을 확인하고 입력 사용자 ID를 받지 않는다. JSON은 `ApiResponse`로 감싼다.

| API | 결과 |
|---|---|
| `GET /api/v2/recaps` | `months`, 최신순, 없는 경우 빈 배열 |
| `GET /api/v2/recaps/{yearMonth}` | 개인 상세 |
| `GET /api/v2/recaps/{yearMonth}/share` | 공유용 집계·비교·동행자 |
| `GET /api/v2/recaps/{yearMonth}/companion/avatar` | 인증된 고정 사진 바이너리 |

상세 필드는 `yearMonth`, `ownerName`, `generatedAt`, `completedSettlementCount: int`, `totalOwnAmount: long`, `comparison`, `companion`이다. 비교에는 `status`, `previousOwnAmount`, `amountDifference`, `changeRatePercent`를 둔다. 동행자는 `kind`, `displayName`, `avatarUrl`, `completedSettlementCount`, `totalOwnAmount`다.

공유 응답은 본인 표시 정보와 상대 원시 이름·계정 ID·파일명을 제외한다. 공유 표시 이름만 노출하며 사진 주소에도 본인 인증이 필요하다. 월은 `0001-01`~`9999-12`의 엄격한 `yyyy-MM` 형식으로 검증한다. 유효한 월의 저장 결과 없음은 현재·미래 월도 `404 RECAP_NOT_FOUND`, 사진 없음은 `404 RECAP_IMAGE_NOT_FOUND`, 잘못된 형식은 기존 400, 잘못된 인증·세션은 기존 401 계약이다.

### Application과 외부 경계

월 목록·개인 조회·공유 조회·사진 조회 및 내부 생성 UseCase와 plain Result를 추가한다. Application Policy가 요약·비교·동행자 규칙을 처리하고 Service가 원본 사실과 저장을 연결한다.

원본 사실 조회, 스냅샷 조회·삽입, 생성 작업 Store, 사진 Storage·정리, 탈퇴 시 소유 리캡 삭제 Port는 실제 호출자와 Adapter를 함께 구현한다. 회원·월 사실은 한 SQL에서 본인 부담액을 정산별로 먼저 구성해 참여자 조인 중복을 막는다. 미래 Kafka Publisher Port는 만들지 않는다.

### 저장과 설정

- Flyway 필요: **Yes**, `V48__create_monthly_recap_schema.sql`.
- 마이그레이션 PR: [#511](https://github.com/Team-HowMuch/howmuch-backend-v2/pull/511), `200c5b14`에 반영됨.
- `monthly_recaps`: 회원·월 UNIQUE, 고정 요약·비교·동행자·파일명·UTC 생성 시각. UPDATE로 고정 결과를 바꾸지 못하게 한다. 소유자만 FK로 참조하고 상대·원본 정산에는 삭제 연결을 두지 않는다.
- `recap_generation_state`: singleton, 최초 대상 월·등록 완료 월·UTC 감사 시각.
- `recap_generation_jobs`: 회원·월 UNIQUE, 상태·시도 횟수·재시도·점유 토큰/만료·예약 파일·완료/실패/skip 정보.
- `recap_image_cleanup_tasks`: 파일명 UNIQUE, 상태·점유·시도·재시도·실패 정보. 파일 삭제 성공 후 작업을 제거한다.
- 월 첫날·지원 연도·금액/건수·비교 필드 결합·동행자 필드 결합·작업 상태별 NULL 규칙을 DB 제약으로 보호한다.
- `RECAP_IMAGE_STORAGE_DIR`, 기본 `./uploads/recap-images`. 영구 저장소와 다중 인스턴스 공유 경로가 출시 선행 조건이다.
- Redis 계약과 기존 알림 schema는 변경하지 않는다.

## 5. 설계 결정

| 결정 | 이유·한계 |
|---|---|
| 직전 저장 리캡 비교 | 과거 결과 고정 및 생성 실패 월의 순서 보장 |

| 비교율 SQL의 소수 정밀도 30자리 | BIGINT 경계에서 기본 numeric 나눗셈이 반올림 경계를 넘는 문제를 재현하고 차단 |
